# Investigation: "Simplify = {}" in HTML Output

## Issue
When rendering FractionAnswer.pg, the HTML output shows an unexpected line:
```
Simplify = {}
Simplify $$\frac{6}{4}$$.
```

The first line `Simplify = {}` should not appear.

## Analysis

### PGML Source
The original Perl file has:
```perl
BEGIN_PGML
Simplify [``\frac{6}{4}``].

Answer = [_]{$answer->cmp(...)}
END_PGML
```

### Problem File After Conversion
The converted Python file shows:
```python
PGML_BLOCK_0 = '''
Simplify = {}
Simplify [``\\frac{6}{4}``].

Answer = [_]{answer.cmp(...)}
'''
```

The `Simplify = {}` line is being added during the Perl → Python conversion.

### Root Cause Candidates

1. **Variable Initialization** (pg_preprocessor_pygment.py, lines 1156-1250)
   - The `_initialize_arrays()` function detects variables used with bracket notation and initializes them
   - However, this should only run on extracted code, not PGML block content (which is inside quoted strings)
   - Ruled out after analysis

2. **PGML Block Extraction** (pg_preprocessor_pygment.py, lines 824-876)
   - PGML blocks are correctly extracted from BEGIN_PGML to END_PGML
   - The extracted content should be clean without the `= {}` line
   - Verified that raw extraction from .pg file shows no `= {}` line

3. **Variable Interpolation** (renderer/pgml.py, line 32)
   - The PGML renderer has a regex `r'\[\$?([a-zA-Z]\w*)\]'` that matches `[varname]` patterns
   - If `Simplify` were a variable in the namespace and appeared in brackets `[Simplify]`, it would be interpolated
   - But the actual PGML text shows `Simplify [``...``]` not `[Simplify]`

4. **Variable Conversion Issue**
   - The line looks like Python dict initialization syntax: `Simplify = {}`
   - This could be generated by something interpreting a Perl assignment pattern incorrectly

## Observations

1. The "Simplify" word appears at the start of the actual problem statement
2. The `= {}` looks like dict initialization (Python) or empty hash assignment (Perl)
3. The preprocessor must be generating this during PGML block extraction or transformation
4. The issue is deterministic and reproducible

## Next Steps for Investigation

1. Instrument the preprocessor to log:
   - Raw extracted PGML block content
   - Block content after `_transform_pgml_evaluators()`
   - The final Python code before PGML block is stored

2. Check if there's a template or special handling for the first line of PGML blocks

3. Look for any place where "Answer = [...]" is being parsed incorrectly and creating variable initializations

4. Check the `_transform_pgml_evaluators()` function (line 3709) more carefully - it processes braces and may be mishandling the PGML content

## Current Status

The three main issues have been resolved:
- ✅ Answer checking works
- ✅ Fraction reduction validation works
- ✅ LaTeX rendering is fixed

The "Simplify = {}" is a cosmetic issue in the HTML output that doesn't affect functionality but should be cleaned up.

## Hypothesis

The most likely cause is that the `_transform_pgml_evaluators()` function or the variable wrapping logic is incorrectly processing the PGML block content and adding variable initialization statements.  Since the answer blank pattern `Answer = [_]{...}` uses `Answer` as a variable name with bracket notation, it might be triggering initialization code that should only run on non-PGML code.

## File Generation

The FractionAnswer.py file is being generated by the `convert_pg_file()` function in `pg_preprocessor_pygment.py` when called with `standalone=True`. This is invoked through the CLI tool:

```bash
python -m pg.translator.cli FractionAnswer.pg --standalone
```

This generates a standalone executable Python file from the .pg source.

## Likely Root Cause

During the preprocessing of the PGML block, the code that wraps list assignments with `PerlList()` (lines 1064-1134) is likely being applied to the PGML block content AFTER it's been extracted but before it's properly protected from processing.

Alternatively, the `_initialize_arrays()` function (line 1156-1250) might be detecting `Answer[...]` patterns within the PGML block and adding initialization: `Answer = {}`.

The fix would require ensuring that PGML block content is not processed by:
1. Variable initialization code (`_initialize_arrays()`)
2. List wrapping code (`wrap_with_perllist_nested()`)

Both should only apply to the executable Python code outside of PGML blocks.
